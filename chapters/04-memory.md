# 第 4 章　记忆

第三章结束时的 agent 已经能调用工具、能接 MCP，但有一个明显的缺口：它记不住上一次说的话。这件事比听起来严重。`messages` 只活在进程里，程序退一下就没了；就算不退出，这个列表也只会单调变长，长到某个点之后，agent 不是在"回忆"，而是在"被历史压着走"。

这一章不打算只给一个裁剪函数就收尾。记忆是一个可以被设计、被度量、被取舍的系统，它有明确的输入输出，也有明确的失败方式。把它当成"把历史拼长一点"来处理，通常在两周后就会撞墙。

## 1. 窗口变长，不等于记得更多

先要理解上下文窗口到底是什么。

Transformer 的每一层里，每个 token 都要和前面所有 token 计算相关性。这意味着两件事：计算量随长度平方增长，缓存所有中间状态的 KV cache 随长度线性增长。这是工程上的约束，但它不是最麻烦的那个。

真正麻烦的是效果。2023 年的一篇论文把关键信息放在长文档的不同位置，测量模型能不能找出来，结果是一条 U 形曲线：信息在开头和结尾时准确率最高，放在中间时明显下降。这个现象后来被称为"中间失忆"（lost in the middle）。它不是某个模型的缺陷，而是训练分布和注意力机制共同作用的结果，换了模型也只是程度上好一点。

有人会说，现在动辄几十万 token 的窗口，针在大海捞针的测试早就满分了。但"能找出一个孤立的事实"和"能用它做推理"是两回事。后续的评测（比如 RULER 系列）把任务换成多跳问答、聚合统计、追踪变量，结论一致：可用长度远小于标称长度，任务越复杂，退化越早。

所以把全部历史塞进窗口，只是满足了"信息在场"，没有满足"信息可用"。记忆系统的第一个任务不是省 token，而是保证关键信息落在模型真正会用到的位置上。

## 2. 成本结构：为什么压缩是必答题

第二个理由是钱。这件事值得算清楚，因为它决定了压缩的收益曲线。

请求是无状态的，每一轮都要把完整历史重发一遍。设每轮新增 t 个 token，第 i 轮要发 i 倍的 t，到第 n 轮为止的总输入是：

```
t + 2t + 3t + ... + nt = t · n(n+1)/2
```

取 t = 400、n = 20，总输入是 84,000 token。对话翻倍到 40 轮，总输入变成 328,000，四倍多。对话长度线性增长，账单是平方增长，这就是"聊久了特别贵"的来源。

不过这里有一个前提正在被改变：prompt caching。DeepSeek、OpenAI、Anthropic 都提供了某种形式的前缀缓存，同一段前缀在短时间内重复发送时，命中的部分按更低的价格计费。历史是天然的前缀，所以长对话最贵的那部分恰好是缓存最可能命中的部分。

缓存改变的是经济性，不改变另外两个约束。窗口还是那么大，注意力还是会在中间衰减。而且缓存有失效时间，几分钟不聊就没了，下一轮又是全价。所以压缩仍然要做，只是目标从"尽量短"变成"把预算花在不可缓存的新信息上"。

还有第三个变量容易被忽略：工具返回的内容也进上下文。第三章的 `run_command` 返回一段测试日志，`view` 返回两百行代码，一次调用就顶几十轮对话。记忆管理不只是管对话，还得管观察结果。

## 3. 五个动作

把记忆当成一个系统来设计，可以拆成五个动作，每个动作都有独立的取舍，而且彼此耦合。

**写**：哪些信息值得从这一轮回流到未来。写多了是噪声，写少了会断片。

**存**：写下来的东西怎么组织，什么时候算过期，两条矛盾的记录怎么处理。

**取**：用户提了一个问题，怎么把相关的旧信息捞出来，捞多少条，阈值怎么定。

**压**：超出预算时，把哪些历史压成摘要，压到什么粒度，丢掉的细节还找不回来。

**装**：最后怎么拼成一次请求——摘要、召回、近期原文，各自占多少，谁放前面。

下面按这个顺序讲。每一节都会指出当前实现做到了哪一步，以及再往前走需要什么。

## 4. 写：什么值得记

最省事的做法是全量写入：每一轮问答都进库。它很快会显出四个问题。

第一是噪声。用户问"今天几号"，助手答"11 月 5 日"，这条信息后天就没有价值了，但它会一直躺在库里，稀释检索的分母。第二是隐私，聊过的路径、密钥、邮箱全进了明文文件。第三是检索质量，库里九成是寒暄时，真正有用的那一成很难被捞到。第四是成本，存和取都不是免费的。

所以需要一个写入闸门。判断"值不值得记"，本质上是判断这条信息的半衰期：几分钟后就没用的（"帮我算一下"）半衰期近乎零；一周后还有用的（"我在用 Python 3.12"）值得留；永远有用的（"我对海鲜过敏"）必须留。

判断信号里最可靠的是**显式指令**。"记住这个""以后都用中文""别再推荐那本书"，用户已经替你做了一次重要性标注，忽略它是最容易犯的错。其次是**实体与约束**：名字、偏好、时间安排、禁止事项。再其次是**决定与结论**，尤其是工具验证过的结论（"跑了一遍，测试是过的"），因为这是花钱换来的信息。

粒度是另一个维度。存一轮问答、存一条事实、还是存一个决策，三种粒度对应三种后续用法：问答适合当语境，事实适合回答提问，决策适合防止反复讨论同一件事。粒度越细，检索越准，但抽取的代价越高——抽事实需要一次额外的模型调用，而且要处理抽取错误。

这里有一个不对称的代价，值得单独说。漏记一条信息，最坏的结果是用户再说一遍。错记一条信息，模型会把它当成事实，在后续对话里反复引用，而用户可能根本没注意到。所以闸门应该偏向保守：宁可不记，不要记错。这也是为什么"摘要里写错了数字"比"摘要里少写了一件事"危险得多。

当前的实现没有做真正的闸门，用户消息和助手的结论都会入库，靠检索时的阈值来过滤。这是一个可以接受的起点，但它意味着库会膨胀，长期使用需要定时清理。

## 5. 存：时间、冲突与身份

存下来之后，最先遇到的问题是时间。

一条记录至少有两个时间：它描述的事情发生在什么时候，以及它是什么时候被记下来的。这两者经常不同。"我明天要去北京"是今天说的，但事情发生在明天；一周后再问"我在哪"，这句话已经过期了，可它的记录时间还很新。只存一个时间戳，就没法区分"旧事实"和"旧记录"。

学术上把这种双时间轴叫 bitemporal，实现起来不复杂：`valid_from` 和 `valid_to` 描述事实的有效区间，`recorded_at` 描述写入时间。检索时按当前时间过滤 `valid_to IS NULL` 或 `valid_to > now`，就能自动跳过过期事实。

第二个问题是冲突。用户先说"我在用 Python"，三天后说"我改用 TypeScript 了"。两条都真实发生过，但只有一条是当前的。没有版本机制时，检索会同时召回两条，模型只能靠时间戳猜，猜错的概率不低。

三种常见解法，复杂度递增。最简单的是查询时按时间倒序、只取最新的 N 条，前提是同一个属性不会有很多条。稍好一点的是给记录加 `supersedes` 指针，新记录指向它取代的旧记录，检索时过滤掉被取代的。最完整的是维护一张"当前事实"表，写入时做 upsert，历史留在另一张表里做审计。

第三个问题是身份。同一个实体可能有很多种称呼："我""小明""用户"，甚至"博主"。检索时不做归一，"我叫小明"和"我的项目"就会被当成两件不相干的事。实体归一需要抽取，抽取需要模型，这是后面结构化的内容。

当前的实现只存了一个 `t` 字段，能按时间排序，但不能表达有效期，也不能表达取代关系。它够用来做"最近说过什么"，不够用来回答"我现在是什么状态"。

## 6. 取：相似度不是充分条件

检索的质量决定了记忆有没有用。这一块有三条独立的轴线。

**词面还是语义。** 稀疏检索（BM25 一类）靠词的重合度打分，快、可解释、不需要额外服务，缺点是同义词和改写全无办法。稠密检索（embedding）把句子映射成向量，靠距离找相似，能处理"我那个 agent 工程"和"agent 学习项目"这种改写，代价是要调 embedding 接口，多一次网络往返，还要把用户数据发出去。实践中常见的是混合：先稀疏召回一批，再用向量或交叉编码器重排（rerank）。

中文还有一层额外的麻烦：BM25 需要词，而中文没有空格。工程上有三种处理，jieba 之类的分词器、字符 n-gram、以及模型自带的 tokenizer。当前实现用的是字符二元组，"我叫小明"被切成"我叫""叫小""小明"，粗糙但不需要任何依赖，对短查询意外地好用，对长文档会产生大量无意义的组合。

**阈值比数量重要。** 召回三条不相关的记忆，比一条都不召回更糟——模型会把它们当事实，而且它们会挤占当前任务的位置。经验上，宁可少召回，召回的内容也要标注来源和不确定性，让模型自己判断可信度。当前实现用的是余弦相似度加一个 0.08 的门槛，这个数字是试出来的，换数据集就要重调。

**打分不应该只有相似度。** 想象两条记忆：一条是三个月前用户随口说的偏好，一条是昨天刚确认的需求，它们和当前问题的相似度一样。只按相似度排序，前者可能排在前面，但它更可能已经过时。 Generative Agents 那篇工作给出的办法是三个因子加权：相似度、时间新近度、重要性。新近度用指数衰减，重要性由模型在写入时打分。

这里有一个容易忽略的细节：**语义记忆不该衰减**。"我对海鲜过敏"是三年前说的，今天依然成立；"我明天要去北京"是昨天说的，今天已经过期。前者是事实，后者是事件，两者的衰减曲线必须不同。当前实现把这两类混在一起，都用同一个时间衰减，这是它的一个明确缺陷。

**去冗余。** 三条几乎一样的记忆，等于一条，而且占了三倍的位置。检索之后做一次 MMR（最大边际相关）或者简单的相似度去重，能明显提升单位预算的信息量。

## 7. 压：摘要是有损的，误差会累积

裁剪和摘要是两件不同的事。裁剪是丢掉，摘要是改写。丢掉的东西找不回来，改写的东西会失真，两者都不可逆。

裁剪看起来比摘要安全，但它有一个硬约束。第三章里，带 `tool_calls` 的 assistant 消息和随后的 `tool` 消息必须配对；如果切点正好落在 `tool` 上，就产生了一条引用已删除调用的孤儿消息，下一轮请求直接 400。所以切点要往回退到安全的位置：

```python
cut = len(self.messages) - KEEP_RECENT
while cut > 0 and self.messages[cut]["role"] == "tool":
    cut -= 1
```

这类 bug 在短对话里永远不出现，只有历史长到真的开始裁剪时才暴露，属于典型的"上线第三周才发现"。

摘要的核心问题是误差累积。第一次压缩，模型把十轮对话变成两百字，丢掉了一些细节，也引入了一点措辞上的偏差。第二次压缩，它读着这份已经失真的摘要，再压一次，偏差被继承并放大。压到第十次，摘要和原始对话可能已经没什么关系了，而且这个过程没有任何报错，你只会觉得"它怎么变笨了"。

对抗误差累积有几个办法，都不完美。

结构化是最有效的。让摘要按固定字段输出——用户目标、已确认事实、做出的决定、未完成事项——模型就没那么容易在自由改写中丢关键信息，而且字段本身提示了"哪些东西不能丢"。当前实现的提示词就是按这个思路写的。

保留锚点也很重要。摘要可以压，但最近若干轮的原文必须保留，作为"当前状态"的校准。每次压缩时对比一下摘要和原文，如果对不上，以原文为准重写摘要。

还有一些细节上的失真特别常见，值得单独防：否定句（"不要用 X" 压成 "用 X"）、数字和日期、条件（"如果 A 就 B"变成"B"）。这些都是 LLM 摘要的老毛病，结构化加锚点能减轻，但消灭不了。

最后是压缩本身的成本。压缩要调一次模型，输入是被压掉的原文，输出是摘要。它不便宜，所以不能每轮都压；触发点应该设得保守，让压缩发生在"再不压就要爆"的时候，而不是"稍微有点长"的时候。

超长历史的场景（比如一次导入几百页文档）还要用分层摘要：先按段压，再把段摘要汇总成总摘要，也就是 map-reduce 的思路。单次压缩塞不下全部输入时，这是唯一的办法。

## 8. 装：预算、顺序与位置

前面四个动作都是为了最后一次拼装。拼装决定了模型在这一次请求里到底能看到什么，以及看到的顺序。

预算分配没有标准答案，但有一个经验比例可以参考：系统提示（角色、规则、工具约定）占一成，召回的记忆占一成半，摘要占两成，最近原文占四成半，给输出留一成。比例本身不重要，重要的是**每一项都有上限**，不会因为某一项突然变长而把其他项挤没。

顺序上，当前实现用的是"系统提示 → 摘要 → 召回 → 近期原文"。把摘要和召回放进系统提示，是因为它们属于背景知识；近期原文放在后面，因为它和当前问题最相关，位置更靠近输入末尾，不容易被中间失忆影响。

位置本身是一个可以利用的变量。既然模型对开头和结尾更敏感，那关键约束就该放在这两处：角色和红线写在系统提示最前面，当前任务的目标写在用户消息的最后。中间部分放那些"在场即可、不需要精确调用"的内容。

还有一个细节是去重。召回的旧记忆和近期原文经常重叠——同一件事在摘要里有一句，在最近三轮里也有原文。重复的内容不但浪费预算，还会让模型误以为这件事被强调过。拼装之前做一次去重是值得的。

这套"把上下文当资源来分配"的思路，在 MemGPT 那篇工作里被推到了极致：它把上下文窗口当内存，把外部存储当磁盘，满了就换页，需要时再读回来，用工具调用模拟操作系统的缺页中断。听起来很重，但当任务跨越几十上百轮时，这种显式的换入换出比任何"自动摘要"都可控，因为你随时知道什么在内存里、什么在磁盘上。

## 9. 评估：怎么知道记忆有用

一个没有评估的记忆系统，只能靠感觉调参，而感觉在长对话里非常不可靠。

最基本的评估方法是构造探针问题：在对话的前半段埋一条信息，后面隔十几轮再问它。这条信息的答案只能来自记忆，不能来自当前上下文，于是"答对了"就说明召回或摘要起了作用。探针要覆盖几种类型——事实（我叫什么）、偏好（我喜欢什么）、决定（我们上次说好用哪个方案）、否定（我说过不要什么）。否定类最容易失败，因为摘要和召回都可能把它丢掉或反转。

指标至少四个：回答准确率、错误记忆率（召回了不相关内容并当真）、平均输入 token、端到端延迟。四个指标要一起看，因为它们的取舍是明确的——召回越多，准确率可能上升，但 token 和延迟也上升，而且错误记忆率往往同步上升。

消融实验是最有说服力的：关掉摘要，看第 30 轮的准确率掉多少；关掉召回，看跨会话的问题还能不能答；把预算砍半，看最先坏掉的是哪一类问题。这些数字比任何架构图都能说明系统到底靠哪一部分在工作。

最后一个容易忽略的维度是长度漂移。同一个问题，在第 5 轮问和第 50 轮问，答案应该一致。如果第 50 轮的答案变差了，说明压缩在丢信息；如果答案变了但更"自信"，说明摘要里混进了错误。

当前实现没有内置评测，`memory.jsonl` 是纯文本，手工构造探针也不算麻烦。这件事在练习里做。

## 10. 代码里有什么，没有什么

`code/ch04_memory.py` 实现了五个动作里最朴素的那一版：

- 写：每轮用户消息和助手结论都进库，没有重要性判断。
- 存：一个追加写的 JSONL，只有记录时间，没有有效期和取代关系。
- 取：字符二元组的余弦相似度，加一个经验阈值，最多三条。
- 压：超预算时把最早的若干条压成增量摘要，保留最近六条原文，工具输出过长时截断。
- 装：摘要和召回都拼进系统提示，然后是近期原文。

它刻意省掉了重要性打分、时间衰减、冲突消解、去重和评估。这些不是遗漏，是留给后面的：每加一个，代码会长一截，而你现在需要的是先看清主干。第 12 节的练习里会让你补上其中几个，补的时候能直观感受到每一项的真实成本。

## 11. 已知的失败模式

把这一章讲的东西反过来看，就是一个失败清单，遇到问题时可以逐条对。

摘要写完就丢、原文不留，导致模型反复重读同一个文件。召回阈值太低，把三个月前的寒暄当成偏好，回答开始跑偏。只记用户的提问、不记结论，跨会话时只知道"问过什么"，不知道"得出过什么"。摘要里否定句被反转，"不要用 TypeScript" 变成"用 TypeScript"，而且没有任何报错。长时间不清理，库里塞满了"你好""谢谢"，检索时全是噪声。密钥和隐私跟着对话进了明文文件，还提交到了 git。

## 12. 动手改一改

1. 给 `Store.add` 加一个重要性参数，用规则判断（含"记住""我叫""偏好"给高分），低于阈值不入库，观察库的大小和召回质量怎么变。
2. 实现时间衰减：`score = 相似度 × exp(-天数/τ)`，把 τ 从 7 天调到 90 天，看召回的内容有什么不同。
3. 给每条记录加 `kind` 字段（fact / event），事实不做时间衰减，事件做。构造一个"三个月前说过过敏、昨天说要去北京"的场景，验证两条记忆的召回行为是否如预期。
4. 写五个探针问题，在第 5 轮和第 30 轮各问一次，记录准确率。这是这一章最值得做的一件事。
5. 把摘要提示词改成结构化输出（目标/事实/决定/待办），对比一下自由摘要丢了多少信息。
6. 实现冲突消解的最简版本：同一属性写入新值时，把旧记录的 `valid_to` 补上，检索时过滤掉过期的。
7. 想一想：如果用户说"忘掉我刚才说的密码"，这套结构要怎么实现？只删 JSONL 里的一行够吗？

## 13. 延伸阅读

按"先看问题、再看方案"的顺序：

- Liu et al., *Lost in the Middle: How Language Models Use Long Contexts*（2023）——U 形曲线的原始实验，读前三节就够。
- Hsieh et al., *RULER: What's the Real Context Size of Your Long-Context Language Models?*（2024）——把"标称窗口"和"可用窗口"分开度量。
- Park et al., *Generative Agents: Interactive Simulacra of Human Behavior*（2023）——记忆流 + 相似度/新近度/重要性三因子检索，本章第 6 节那套打分的出处。
- Packer et al., *MemGPT: Towards LLMs as Operating Systems*（2023）——把上下文当内存管理，分页换入换出。
- Robertson & Zaragoza, *The Probabilistic Relevance Framework: BM25 and Beyond*（2009）——BM25 的完整推导，想做稀疏检索时值得翻。

## 14. 下一章

下一章讲规划。现在的 agent 是走一步看一步，遇到需要五六步的任务，它经常走到一半就偏了，或者反复做同一件事。规划要回答的是：怎么在动手之前把任务拆开、拆到什么粒度、执行中发现计划不对时怎么改，以及"计划的计划"——什么时候该重新规划而不是硬撑。
